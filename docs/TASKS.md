# xiangqi-coach｜任務與順序

這個專案預期讓你長時間自己做。照里程碑的順序做；每個里程碑做完更新 `docs/PROGRESS.md` 再往下。工作規則在 `AGENTS.md`。

## 開始的指令

把這段貼給負責實作的 AI：

> 讀 `AGENTS.md`，再照它寫的順序讀 `docs/` 裡的四份文件。然後從 M0 開始，照 `docs/TASKS.md` 的順序一個里程碑一個里程碑做。每個里程碑先寫測試再實作，做完更新 `docs/PROGRESS.md`。除了 AGENTS.md 列的三種情況與標了「停」的檢查點，不用停下來問我；規格沒寫到的事你自己決定並記在 `docs/DECISIONS.md`。

## 相依關係

```
M0 → M1 → M2 → M3 ──────────────┐
            └→ M4 → M5（持續）   │
                 └→ M6 → M7 → M8 → M9 → M11
                      └→ M10
```

M3（棋譜格式）與 M4（搜尋）互不相依，哪個卡住就先做另一個。
M5（棋力）沒有終點：M4 之後，其他里程碑之間有空就回來做一輪。

---

## M0｜骨架

- Cargo workspace，五個 crate 的空殼，`web/` 的空專案。
- `make check` 可以跑而且是綠的。
- GitHub Actions：一般檢查一個工作，慢速測試另一個工作（手動觸發或每天一次）。
- 建立 `docs/PROGRESS.md`、`docs/DECISIONS.md`、`docs/STRENGTH.md`、`docs/IDEAS.md` 四個空檔，各有一行說明用途。

## M1｜棋盤與走法產生

對應 SPEC 第 5.1、5.2 節，TEST_PLAN 第 2 節、第 4.1 節的 FEN 部分。

- 先查證 perft 的六個數字。
- 棋盤表示法你自己選（陣列或位元棋盤都可以），把理由記在 DECISIONS。
- 另外寫一個「慢但簡單」的走法產生器當對照（產生所有看起來能走的步，逐一試走再檢查將帥），測試裡拿它跟正式的互相比對。
- **做完的標準**：初始局面 perft 1 到 4 全對；perft(4) 少於 1 秒。

## M2｜規則

對應 SPEC 第 5.3 節，TEST_PLAN 第 2.2、第 3 節。

- 將軍、將死、困斃、重複、長將、無吃子步數。
- 第 2.2 節的八個以上局面與答案。能取得 Pikafish 就用它產生答案；不能就照那一節寫的退路做，並在 PROGRESS 註明。
- **做完的標準**：第 2、3 節的測試全綠。

## M3｜棋譜格式

對應 SPEC 第 7 節，TEST_PLAN 第 4 節。

- 順序：座標記譜 → 中文記譜 → PGN 樣式 → 東萍 → 自動判斷。
- 東萍格式先找真實樣本驗證（SPEC 第 7.3 節）。
- 手機 App 的棋局：先查，照 SPEC 第 7.5 節處理，結果記在 DECISIONS。**這一項查不到不算失敗**，照實記錄就好。
- **做完的標準**：第 4 節的測試全綠；隨機棋局的來回轉換 200 盤全對。

## M4｜搜尋與 UCI

對應 SPEC 第 6.1 節，TEST_PLAN 第 5.1、5.3（第 1、2 條）、5.5 節。

- 最基本的搜尋與評估，先求正確。
- `xq-uci`：UCI 協定、perft 指令、兩個引擎對打的比賽程式（可以指定節點數、開局集、盤數，輸出勝和負與等級分差）。
- M4 基準 gate 沿用既有 50 個開局與 30 題殺棋題，註明出處；TT 等正確性修復依 TEST_PLAN §5.3.5 保持原 50 局／200 盤驗收。所有尚未開始的棋力增強候選（包括新的 M4 組合與 M5 候選）依 TEST_PLAN §5.2 從剩餘 153 局事前抽定 ordered100、分兩組 50 驗收。已定案試驗不重抽、不改判。
- **做完的標準**：第 5.1、5.5 節全綠；對隨機走法 1000 盤全勝；對貪心 98% 以上。
- 這是 `docs/STRENGTH.md` 的第一列：基準版。

## M5｜讓它變強（持續）

對應 SPEC 第 6.2、6.3、6.4 節，TEST_PLAN 第 5.2、5.3、5.4 節。

- 一次加一項技術，照 TEST_PLAN 第 5.2 節量，留或還原，記進 STRENGTH；新候選須等 source/config 凍結後才抽 seed 與 ordered100。新的 M4 組合候選也適用同一抽樣規則；不追溯更動既有結果。
- 至少做完這些再往 M6 走：置換表的各種用法、靜態搜尋、走法排序（吃子排序、殺手、歷史表）、空著裁剪、後期走法縮減、將軍延伸。
- 之後有空再做：渴望窗口、時間管理、評估參數自動調整、開局庫。
- 定義十個難度等級並驗證（第 5.3 節第 3 條）。
- 用自己對打的棋局校正勝率公式的 k（TEST_PLAN 第 6.1 節第 5 條）。

**停：做完 M5 的最低要求後，在 PROGRESS 寫一段給使用者的摘要**（現在多強、試了哪些有用哪些沒用、十個等級的對打結果），然後繼續做 M6，不用等回覆。

## M6｜網頁上可以下棋

對應 SPEC 第 3、4、10 節，TEST_PLAN 第 8 節第 1、2 條。

- `xq-wasm`；引擎放 Web Worker；畫面與引擎之間用訊息介面（SPEC 第 11 節的要求）。
- 棋盤、對弈、悔棋、難度、棋譜顯示（中文記譜）。
- 部署到 GitHub Pages。
- **做完的標準**：端到端第 1、2 條通過；在手機寬度的畫面可以下完一盤。

## M7｜覆盤的骨幹

對應 SPEC 第 8.1、8.2、8.3、8.6、8.7 節，TEST_PLAN 第 6.1、6.2、6.5 節。

- `Analyzer` 介面、內建分析器、測試用的假分析器。
- 兩輪分析、勝率曲線、分類、候選走法、「想更久」。
- 推演：分支樹、退回、註解。
- 即時勝率。
- 棋局庫與本機儲存。
- **做完的標準**：第 6.1、6.2、6.5 節全綠；端到端第 3、4、5、8 條通過。

## M8｜為什麼，以及配合程度

對應 SPEC 第 8.4、8.5 節，TEST_PLAN 第 6.3、6.4 節。

- 八種原因的判斷與模板，三種寫法（入門初學、中等、熟練高手）。
- 程度估計與它的驗證。
- **做完的標準**：第 6.3、6.4 節全綠。

**停：M8 做完後，用引擎自己對打產生三盤棋，各產生一份覆盤結果（三種程度各一份），存進 `docs/samples/`，在 PROGRESS 請使用者看講解的句子自不自然。** 然後繼續做 M9，不用等回覆。

## M9｜匯入畫面與筆記

對應 SPEC 第 7.6、9 節，TEST_PLAN 第 7 節、第 8 節第 6、7 條。

- 匯入畫面接上 M3 的格式。
- 筆記產生、複製成文字、下載圖。
- 整包匯出與匯入。
- **做完的標準**：第 7 節全綠；端到端第 6、7 條通過。把一份範例筆記存進 `docs/samples/`。

## M10｜外接強引擎

對應 SPEC 第 4.1 節，TEST_PLAN 第 5.4 節。

- `UciAnalyzer`：啟動外部引擎的執行檔、送指令、讀結果、逾時處理、對方當掉時的處理。用一個假的 UCI 引擎（幾行的腳本）測這些情況。
- 命令列加一個指令：給一份棋譜與外部引擎的路徑，輸出覆盤結果與筆記。這樣不靠網頁也能用強引擎覆盤。
- 查 Pikafish 有沒有可以在瀏覽器裡用的 WebAssembly 版本、授權與載入方式。有：做成使用者自己提供檔案或網址才載入的外掛，不放進 repo。沒有或不確定：網頁版只用內建引擎，畫面上說明，把查到的情況記在 DECISIONS。
- **授權的界線見 AGENTS.md 第 6 條，不可以越過。**

- **做完的標準**：端到端第 9 條通過。

## 第二階段（2026-10-17，使用者要求）

使用者在 2026-10-16 實際用過網站之後的方向：覆盤要看得懂、介面要分開（一般使用者不看數字，開發者另外看）、覆盤要快、之後搬到 Cloudflare，當成完整的專案經營。下面的順序是建議，使用者可以調換；每一項照舊「先紅測、再實作」，做完寫 PROGRESS。

### 相依關係

```
P0 量測 → P1 編譯優化 → P2 平行覆盤 → P3 結果快取
                                   └→ P6 介面重做（含背景自動覆盤）
P4 講解第二批（與 P0–P3 互不相依）
P5 搬到 Cloudflare（停：要使用者的帳號）→ P7 多執行緒搜尋（選做，要過棋力門檻）
```

### P0｜先量，再優化
- 量三個數字，寫進 PROGRESS：同一局面同一節點數，原生版與網頁 wasm 版的每秒節點數（nps）；範例棋局整盤覆盤在網頁的時間（預估較快、標準兩種節點數）；難度 10 每步時間。
- 量測工具不進 main（照 2026-10-16 卡頓量測的做法，用不合併的量測分支）。
- **做完的標準**：三個數字都有，寫明在哪台機器、哪個 commit、哪個 run 量的。

### P1｜wasm 編譯優化（結果不變）
- release profile 開 `lto`、`codegen-units = 1`；建置流程加 `wasm-opt -O3`；評估 `+simd128`（要確認目標瀏覽器都支援，不支援的話要有退路）。
- 不改任何引擎程式碼。驗收：既有的節點序列、覆盤契約測試全部不動照樣通過；P0 的 nps 前後對照寫進 PROGRESS；wasm 大小變化也記下來。
- 不算棋力改動（搜尋行為完全相同），但要證明「節點數逐步相同」。

### P2｜多個背景工作平行覆盤
- 一盤棋的各步分給 N 個 review worker（N 依 `navigator.hardwareConcurrency`，上限例如 4，手機少開），結果按步數組回。
- **先查清楚**：目前每一步的分析是否沿用前一步的置換表或其他狀態。如果有，拆開之後結果可能和現在不同，要先寫測試定義「同一盤棋、同一設定、不論幾個 worker，結果都一樣」，必要時讓每步從乾淨狀態開始（這可能改變既有期望值，要逐條寫 DECISIONS）。
- 記憶體：每個 worker 各載一份 wasm 和置換表，手機上要量過。
- 取消覆盤要能停掉所有 worker。
- **做完的標準**：決定性測試通過；P0 的覆盤時間前後對照；E2E 全綠。

### P3｜分析結果快取
- 以「局面＋分析設定（節點數、引擎版本）」為鍵，存在 IndexedDB；重新覆盤同一盤、或相同開局時直接取用。
- 引擎或講解規則一改，版本號就換，舊快取作廢。
- **做完的標準**：重新覆盤同一盤的時間大幅下降（量過）；換版本後不會用到舊結果（有測試）。

### P4｜講解第二批（原本排好的）
- 放寬 material_reason（兩條線各取最多 N 步比較）；活動空間講步數（after_best）；新 ReasonKind 炮架（CannonMount，拆 F1 Rust／F2 網頁連動）；SPEC 8.4 與 TEST_PLAN 6.3 第 9 條一起改編號；重新產生 docs/samples（第 37 手的舊講法會換掉）。計畫細節在 2026-10-16 的計畫 v2（見 PROGRESS「覆盤對照句」一節）。

### P5｜搬到 Cloudflare Pages（停）
- **停**：要使用者自己申請 Cloudflare 帳號（免費方案），並建立只有 Pages 部署權限的 API token，存成 GitHub secret。不在對話裡貼 token。
- GitHub Actions 用 wrangler 部署：main → 正式網址，其他分支 → 預覽網址。GitHub Pages 先保留到 Cloudflare 穩定再決定。
- `_headers`：帶雜湊的檔案設長快取（immutable），`index.html` 與 service worker 不快取；wasm 走 brotli。
- COOP/COEP 標頭先不開，等 P7 決定要做才開；開之前確認離線安裝、更新提示、子路徑 wasm 都照常（既有 E2E 加跑在預覽網址上）。
- 選做：自訂網域（使用者有網域才做）。
- **做完的標準**：正式網址與預覽網址都能下棋、覆盤、離線；既有 E2E 對 Cloudflare 預覽網址跑過一次。

### P6｜介面重做（照 2026-10-16 草圖）
- 分頁「下棋／覆盤／棋譜庫」、下完的「覆盤這盤」按鈕、齒輪設定（分層）、開發者模式才看得到分數／深度／節點數／預算與候選列分數。
- 下完一盤自動在背景覆盤（用 P2 的平行覆盤），程度估計顯示「已下 N 盤，M 盤已計入」。
- 順手收掉 2026-10-16 覆盤悔棋修正留下的選改（renderLiveProbability 結構、回合表不隨存檔保存）。

### P7｜多執行緒搜尋（選做，要 P5 與棋力門檻）
- 需要 COOP/COEP（P5 上開）與 SharedArrayBuffer；做法例如 Lazy SMP。
- 同一局面每次結果可能不同，違反「引擎結果固定」，所以只能當下棋時的選項，覆盤與所有測試仍用單執行緒。
- 這是棋力改動：照 TEST_PLAN 第 5 節對打門檻驗收，沒過就還原並寫 STRENGTH.md。
- 「趁使用者思考時先算」（pondering）同樣是棋力改動，排在這之後，放 IDEAS。
