# xiangqi-coach｜任務與順序

這個專案預期讓你長時間自己做。照里程碑的順序做；每個里程碑做完更新 `docs/PROGRESS.md` 再往下。工作規則在 `AGENTS.md`。

## 開始的指令

把這段貼給負責實作的 AI：

> 讀 `AGENTS.md`，再照它寫的順序讀 `docs/` 裡的四份文件。然後從 M0 開始，照 `docs/TASKS.md` 的順序一個里程碑一個里程碑做。每個里程碑先寫測試再實作，做完更新 `docs/PROGRESS.md`。除了 AGENTS.md 列的三種情況與標了「停」的檢查點，不用停下來問我；規格沒寫到的事你自己決定並記在 `docs/DECISIONS.md`。

## 相依關係

```
M0 → M1 → M2 → M3 ──────────────┐
            └→ M4 → M5（持續）   │
                 └→ M6 → M7 → M8 → M9 → M11
                      └→ M10
```

M3（棋譜格式）與 M4（搜尋）互不相依，哪個卡住就先做另一個。
M5（棋力）沒有終點：M4 之後，其他里程碑之間有空就回來做一輪。

---

## M0｜骨架

- Cargo workspace，五個 crate 的空殼，`web/` 的空專案。
- `make check` 可以跑而且是綠的。
- GitHub Actions：一般檢查一個工作，慢速測試另一個工作（手動觸發或每天一次）。
- 建立 `docs/PROGRESS.md`、`docs/DECISIONS.md`、`docs/STRENGTH.md`、`docs/IDEAS.md` 四個空檔，各有一行說明用途。

## M1｜棋盤與走法產生

對應 SPEC 第 5.1、5.2 節，TEST_PLAN 第 2 節、第 4.1 節的 FEN 部分。

- 先查證 perft 的六個數字。
- 棋盤表示法你自己選（陣列或位元棋盤都可以），把理由記在 DECISIONS。
- 另外寫一個「慢但簡單」的走法產生器當對照（產生所有看起來能走的步，逐一試走再檢查將帥），測試裡拿它跟正式的互相比對。
- **做完的標準**：初始局面 perft 1 到 4 全對；perft(4) 少於 1 秒。

## M2｜規則

對應 SPEC 第 5.3 節，TEST_PLAN 第 2.2、第 3 節。

- 將軍、將死、困斃、重複、長將、無吃子步數。
- 第 2.2 節的八個以上局面與答案。能取得 Pikafish 就用它產生答案；不能就照那一節寫的退路做，並在 PROGRESS 註明。
- **做完的標準**：第 2、3 節的測試全綠。

## M3｜棋譜格式

對應 SPEC 第 7 節，TEST_PLAN 第 4 節。

- 順序：座標記譜 → 中文記譜 → PGN 樣式 → 東萍 → 自動判斷。
- 東萍格式先找真實樣本驗證（SPEC 第 7.3 節）。
- 手機 App 的棋局：先查，照 SPEC 第 7.5 節處理，結果記在 DECISIONS。**這一項查不到不算失敗**，照實記錄就好。
- **做完的標準**：第 4 節的測試全綠；隨機棋局的來回轉換 200 盤全對。

## M4｜搜尋與 UCI

對應 SPEC 第 6.1 節，TEST_PLAN 第 5.1、5.3（第 1、2 條）、5.5 節。

- 最基本的搜尋與評估，先求正確。
- `xq-uci`：UCI 協定、perft 指令、兩個引擎對打的比賽程式（可以指定節點數、開局集、盤數，輸出勝和負與等級分差）。
- 準備 50 個開局局面與 30 題殺棋題，註明出處。
- **做完的標準**：第 5.1、5.5 節全綠；對隨機走法 1000 盤全勝；對貪心 98% 以上。
- 這是 `docs/STRENGTH.md` 的第一列：基準版。

## M5｜讓它變強（持續）

對應 SPEC 第 6.2、6.3、6.4 節，TEST_PLAN 第 5.2、5.3、5.4 節。

- 一次加一項技術，照第 5.2 節量，留或還原，記進 STRENGTH。
- 至少做完這些再往 M6 走：置換表的各種用法、靜態搜尋、走法排序（吃子排序、殺手、歷史表）、空著裁剪、後期走法縮減、將軍延伸。
- 之後有空再做：渴望窗口、時間管理、評估參數自動調整、開局庫。
- 定義十個難度等級並驗證（第 5.3 節第 3 條）。
- 用自己對打的棋局校正勝率公式的 k（TEST_PLAN 第 6.1 節第 5 條）。

**停：做完 M5 的最低要求後，在 PROGRESS 寫一段給使用者的摘要**（現在多強、試了哪些有用哪些沒用、十個等級的對打結果），然後繼續做 M6，不用等回覆。

## M6｜網頁上可以下棋

對應 SPEC 第 3、4、10 節，TEST_PLAN 第 8 節第 1、2 條。

- `xq-wasm`；引擎放 Web Worker；畫面與引擎之間用訊息介面（SPEC 第 11 節的要求）。
- 棋盤、對弈、悔棋、難度、棋譜顯示（中文記譜）。
- 部署到 GitHub Pages。
- **做完的標準**：端到端第 1、2 條通過；在手機寬度的畫面可以下完一盤。

## M7｜覆盤的骨幹

對應 SPEC 第 8.1、8.2、8.3、8.6、8.7 節，TEST_PLAN 第 6.1、6.2、6.5 節。

- `Analyzer` 介面、內建分析器、測試用的假分析器。
- 兩輪分析、勝率曲線、分類、候選走法、「想更久」。
- 推演：分支樹、退回、註解。
- 即時勝率。
- 棋局庫與本機儲存。
- **做完的標準**：第 6.1、6.2、6.5 節全綠；端到端第 3、4、5、8 條通過。

## M8｜為什麼，以及配合程度

對應 SPEC 第 8.4、8.5 節，TEST_PLAN 第 6.3、6.4 節。

- 八種原因的判斷與模板，三種寫法（入門初學、中等、熟練高手）。
- 程度估計與它的驗證。
- **做完的標準**：第 6.3、6.4 節全綠。

**停：M8 做完後，用引擎自己對打產生三盤棋，各產生一份覆盤結果（三種程度各一份），存進 `docs/samples/`，在 PROGRESS 請使用者看講解的句子自不自然。** 然後繼續做 M9，不用等回覆。

## M9｜匯入畫面與筆記

對應 SPEC 第 7.6、9 節，TEST_PLAN 第 7 節、第 8 節第 6、7 條。

- 匯入畫面接上 M3 的格式。
- 筆記產生、複製成文字、下載圖。
- 整包匯出與匯入。
- **做完的標準**：第 7 節全綠；端到端第 6、7 條通過。把一份範例筆記存進 `docs/samples/`。

## M10｜外接強引擎

對應 SPEC 第 4.1 節，TEST_PLAN 第 5.4 節。

- `UciAnalyzer`：啟動外部引擎的執行檔、送指令、讀結果、逾時處理、對方當掉時的處理。用一個假的 UCI 引擎（幾行的腳本）測這些情況。
- 命令列加一個指令：給一份棋譜與外部引擎的路徑，輸出覆盤結果與筆記。這樣不靠網頁也能用強引擎覆盤。
- 查 Pikafish 有沒有可以在瀏覽器裡用的 WebAssembly 版本、授權與載入方式。有：做成使用者自己提供檔案或網址才載入的外掛，不放進 repo。沒有或不確定：網頁版只用內建引擎，畫面上說明，把查到的情況記在 DECISIONS。
- **授權的界線見 AGENTS.md 第 6 條，不可以越過。**

## M11｜離線與安裝

對應 SPEC 第 11 節，TEST_PLAN 第 8 節第 9 條。

- Service Worker、manifest、圖示（用程式畫的，不要用外部圖檔）。
- **做完的標準**：端到端第 9 條通過。

## 全部做完之後

在 PROGRESS 寫一份總結：每個里程碑的狀態、測試總數、最後的棋力數字、所有你自己做的決定的清單、沒做到的事、你認為接下來最值得做的三件事。然後停。
