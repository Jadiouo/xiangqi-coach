# xiangqi-coach｜規格

版本 0.1（2026-10-06）。怎麼驗證在 `TEST_PLAN.md`，做的順序在 `TASKS.md`。

## 1. 這是什麼

一個中國象棋的對弈與覆盤程式。核心是自己寫的引擎；最重要的功能是覆盤。

做完的樣子：

1. 打開網頁可以跟電腦下棋，難度會配合你的程度。
2. 下完按「覆盤」：看到整盤的勝率曲線，下壞的地方有標記；點任何一步，看到當時更好的走法、後續變化、一句為什麼。
3. 覆盤中隨時可以自己動棋子試別的走法，引擎接著應，一路推演下去，可以退回。
4. 覆盤結束可以存成一份筆記。
5. 貼上別人的棋譜，可以用同樣的方式覆盤。
6. repo 裡有一張表，記錄引擎每一版比前一版強多少。

## 2. 不做的事（這一版）

- 不做神經網路評估，不做需要顯示卡的訓練。
- 不做連線對戰、帳號、伺服器。所有資料存在使用者自己的裝置。
- 不用任何 AI 語言模型產生講解。講解全部由規則與模板產生。
- 不實作完整的亞洲棋規或中國棋規的長打細則，只做第 5.3 節的簡化版。
- 不做揭棋、暗棋等變體。
- 不把 Pikafish 或其他引擎的程式碼、權重放進 repo。

## 3. 技術選擇

| 項目 | 選擇 | 理由 |
|---|---|---|
| 引擎語言 | Rust | 快；可以編成 WebAssembly 在瀏覽器跑；之後用 Tauri 包成桌面與手機 App 時是同一種語言 |
| 瀏覽器裡跑引擎 | WebAssembly，放在 Web Worker | 搜尋不能卡住畫面 |
| 畫面 | TypeScript、Vite，棋盤用 SVG | 不用框架；棋子用文字畫，不需要圖檔 |
| 引擎對外協定 | UCI（象棋引擎通用的那一版） | 才能跟別的引擎對打、才能外接 Pikafish |
| 測試 | `cargo test`；畫面用 Vitest；少數端到端用 Playwright | |
| CI | GitHub Actions | |
| 之後包 App | 先做成可安裝的 PWA；再用 Tauri | 這一版只要求 PWA |

## 4. 架構

```
crates/
├── xq-core      棋盤、棋子、走法產生、規則、FEN、各種棋譜格式的讀寫
├── xq-engine    搜尋與評估。只依賴 xq-core
├── xq-review    覆盤：勝率換算、每一步的分類、講解模板、程度估計、筆記產生
├── xq-uci       命令列程式：UCI 協定、perft、兩個引擎對打的比賽程式
└── xq-wasm      把上面的東西包成 WebAssembly 給網頁用
web/             網頁：棋盤、對弈、覆盤、匯入、筆記、設定
docs/
```

依賴方向只能往下：`xq-wasm`、`xq-uci` → `xq-review` → `xq-engine` → `xq-core`。

`xq-core` 與 `xq-engine` 是純的：不讀時鐘、不讀檔案、不自己產生亂數。搜尋的停止條件由呼叫端傳入（節點數上限，或一個「該停了嗎」的回呼）。**同一個局面、同一個節點數上限、同一個設定，一定回傳同一步棋**，這是所有測試的基礎。

### 4.1 分析的來源

覆盤不直接呼叫引擎，而是透過一個介面：

```rust
pub trait Analyzer {
    /// 回傳這個局面的前 n 個候選走法，各自的評分（分，從走棋方看）與主要變化。
    fn analyze(&mut self, pos: &Position, limit: Limit, multipv: usize) -> Vec<Line>;
    fn name(&self) -> String;
}
```

兩個實作：

- `BuiltinAnalyzer`：自己的引擎。一定有。
- `UciAnalyzer`：透過 UCI 跟一個外部引擎的執行檔對話（例如 Pikafish）。使用者在設定裡指定執行檔路徑才啟用。

網頁版能不能用外部引擎是未知數（瀏覽器不能執行本機程式）。處理方式見 TASKS 的 M10：先查有沒有可用的 WebAssembly 版；沒有的話，網頁版只用內建引擎，外部引擎留給命令列與之後的 Tauri 版，並在畫面上說清楚。

覆盤畫面要顯示這次分析是誰做的。

## 5. 棋盤與規則

### 5.1 座標

- 九條直線叫 a 到 i（從紅方的左邊數起），十條橫線叫 0 到 9（紅方底線是 0）。
- 紅方在下，先走。
- 一個走法寫成四個字元：起點加終點，例如 `h2e2`。這是這個專案內部唯一的走法表示。

### 5.2 FEN

沿用通行的象棋 FEN。初始局面：

```
rnbakabnr/9/1c5c1/p1p1p1p1p/9/9/P1P1P1P1P/1C5C1/9/RNBAKABNR w - - 0 1
```

大寫是紅方。字母：K 帥將、A 仕士、B 相象（也接受 E）、N 馬（也接受 H）、R 車、C 炮、P 兵卒。走棋方 `w` 是紅、`b` 是黑。

### 5.3 規則

走法規則照標準象棋：蹩馬腿、塞象眼、相象不過河、仕士與將帥不出九宮、炮隔一子吃、兵卒過河後可橫走、**將帥不能在同一條直線上直接對面**。

勝負：

- 走完之後自己的將帥被攻擊的走法是不合法的。
- 輪到走的一方沒有合法走法：輸（不論有沒有被將軍。象棋的困斃是輸，不是和）。
- 簡化的重複規則：同一個局面第三次出現時判定。如果這段重複裡，有一方每一步都在將軍（長將），那一方輸；否則和棋。長捉不另外判，算和棋。
- 連續 120 步（雙方各 60 步）沒有吃子：和棋。

這套簡化規則跟正式比賽不同，畫面的說明頁要寫明。

## 6. 引擎

### 6.1 最低要求

- 走法產生通過 perft（TEST_PLAN 第 2 節）。
- 搜尋：疊代加深的 alpha-beta、置換表（Zobrist 雜湊）、靜態搜尋、走法排序。
- 評估：子力、位置表、機動性、將帥安全。評估函式要能回傳**各項的明細**（不只是總分），覆盤的講解會用到。
- 支援 MultiPV：一次回傳前 n 個候選走法。
- 能回報將死的步數（幾步殺）。

### 6.2 之後一項一項加、每項都要量過

空著裁剪、後期走法縮減、將軍延伸、殺手走法與歷史表、渴望窗口、時間管理、評估參數的自動調整（用自己對打的棋局做 Texel tuning，只用處理器）。順序你決定，但每一項都要照 TEST_PLAN 第 5 節量過才留下。

### 6.3 難度

難度不是靠「故意亂走」做的，而是三個旋鈕：搜尋的節點數上限、評估裡加的雜訊大小、從前幾名候選裡挑的機率。定義十個等級，等級之間的實際棋力差要用對打驗證（等級高的要贏等級低的）。

### 6.4 棋力紀錄

`docs/STRENGTH.md` 是一張表，每一列是一次引擎的修改：日期、改了什麼、對上一版的勝／和／負、換算的等級分差、信賴區間、留下還是還原。「試過、沒用」的也要記。

## 7. 棋譜格式

全部在 `xq-core`。每一種都要能讀；中文記譜與座標記譜還要能寫。貼進來的文字先自動判斷是哪一種。

### 7.1 座標記譜（ICCS）

`h2e2 h9g7 h0g2 ...`，可以有步數編號、可以用 `-` 連接（`H2-E2`），大小寫不拘。

### 7.2 中文記譜

四個字：棋子、所在直線、動作、目的地。例如 `炮二平五`、`馬8進7`。

- 紅方的直線用中文數字一到九，**從紅方自己的右邊數起**（一是 i 線，九是 a 線）。
- 黑方的直線用阿拉伯數字 1 到 9，**從黑方自己的右邊數起**（1 是 a 線，9 是 i 線）。全形數字也要接受。
- 動作：進、退、平。車炮兵將的進退，後面的數字是走幾格；馬、相、仕的進退與所有的平，後面的數字是目的地的直線。
- 同一條直線上有兩個相同的棋子：用 `前`、`後` 代替直線，例如 `前炮退二`。兵卒有三個以上在同一條線，用 `前`、`中`、`後`；兩條線上各有兩個以上的兵，會出現 `前三進一` 這種寫法（第二個字是直線）。這些少見的寫法要支援，並且要有測試。
- 繁體與簡體都要接受：馬马、車车、砲炮包、帥帅、將将、仕士、相象、兵卒、進进、後后。黑方的棋子名稱（將、士、象、卒）與紅方的（帥、仕、相、兵）在讀的時候不強制區分，以走棋方決定是誰的子。
- 輸出時一律用繁體，紅方用帥仕相兵、黑方用將士象卒。

對照例（中炮對屏風馬的前三回合）：

| 回合 | 紅 | 座標 | 黑 | 座標 |
|---|---|---|---|---|
| 1 | 炮二平五 | h2e2 | 馬8進7 | h9g7 |
| 2 | 馬二進三 | h0g2 | 車9平8 | i9h9 |
| 3 | 車一平二 | i0h0 | 馬2進3 | b9c7 |

### 7.3 東萍格式（DhtmlXQ）

東萍象棋網的棋譜是一段用方括號標籤包起來的文字，例如 `[DhtmlXQ_movelist]...[/DhtmlXQ_movelist]`。

- `DhtmlXQ_movelist`：每四個數字是一步，依序是起點的 x、y 與終點的 x、y。x 是 0 到 8，從紅方的左邊數起；y 是 0 到 9，**從黑方底線往下數**（所以紅方底線是 9）。上面那三回合寫成 `774770627967807089791022`。
- `DhtmlXQ_binit`：開局不是標準局面時才有，64 個數字，32 個棋子各兩位的座標。棋子的順序與「不在棋盤上」的表示法**要自己查證**，找真實的棋譜樣本對過再實作。
- 其他標籤（標題、對局者、結果、註解、變著）：讀得到就保留，讀不懂的忽略，不要當掉。變著（`DhtmlXQ_move_x_y_z` 這類）這一版可以不支援，但要在匯入結果裡告訴使用者「這份棋譜有變著，沒有匯入」。

這一節的格式描述是憑整理者的記憶寫的，**動手前先找三份以上真實的東萍棋譜驗證**，對不上就以真實樣本為準，並記在 `docs/DECISIONS.md`。

### 7.4 PGN 樣式的象棋棋譜

有些網站與軟體用類似西洋棋 PGN 的格式：方括號的標頭（`[Red "..."]`、`[Black "..."]`、`[FEN "..."]`、`[Result "..."]`）加上走法，走法可能是中文記譜或座標記譜。要能讀。

### 7.5 手機 App 的棋局

使用者提到天天象棋、JJ 象棋這類 App。它們實際匯出或分享的是什麼格式，**整理者不知道**。做法：

1. 先查。查得到公開、可解析的文字格式就支援。
2. 如果分享的是網址、圖片，或是私有的二進位格式：不要猜、不要逆向工程。在匯入畫面寫清楚「目前不支援，請改用 App 裡的『複製棋譜』功能（如果有）取得文字棋譜」，並把查到的情況記在 `docs/DECISIONS.md`。

另外，象棋橋的 XQF 是常見的二進位檔。這一版不要求；放進 `docs/IDEAS.md`。

### 7.6 匯入的行為

- 貼上文字 → 自動判斷格式 → 逐步驗證每一步都合法。
- 某一步不合法或有歧義：停在那一步，告訴使用者是第幾步、原文是什麼、為什麼讀不懂。前面讀得懂的部分照樣可以覆盤。
- 匯入成功後顯示：格式、總步數、起始局面是否為標準開局。

## 8. 覆盤

### 8.1 勝率

引擎給的是「分」（一個兵大約 100 分）。換算成勝率：

```
勝率 = 1 / (1 + exp(−分 / k))
```

k 用引擎自己對打的結果校正：收集大量「某個局面的評分」與「那盤棋最後的勝負」，找出讓預測最準的 k。校正前先用 k = 300 當預設值。幾步殺直接算 100% 或 0%。

畫面上的勝率永遠從**使用者那一方**看。匯入別人的棋譜時，預設從紅方看，可以切換。

### 8.2 分析一盤棋

對每一個局面，請分析器給前三名候選走法。然後對每一步棋算：

- **這一步損失的勝率** ＝（當時最佳走法之後的勝率）−（實際走法之後的勝率），都從走棋方看。
- 實際走法是不是前三名之一、是第幾名。
- 最佳走法與它的主要變化（往後至少六步）。

分析要分兩輪：第一輪用少量節點很快掃過整盤，先把曲線畫出來；第二輪把第一輪損失超過 5% 的那些步，用多十倍的節點重新分析。使用者可以對任何一步按「想更久」。

### 8.3 每一步的分類

依損失的勝率：

| 分類 | 損失 | 顯示 |
|---|---|---|
| 好棋 | 小於 2%，且是最佳或次佳 | 不標記 |
| 唯一著 | 是最佳走法，而且次佳走法會多損失 15% 以上 | 特別標記 |
| 緩著 | 2% 到 5% | 小標記 |
| 疑問手 | 5% 到 10% | 標記 |
| 失誤 | 10% 到 20% | 明顯標記 |
| 大漏著 | 20% 以上 | 最明顯的標記 |

已經大勢底定的局面要特別處理：勝率已經高於 95% 或低於 5% 時，損失的百分比不代表什麼，改看「有沒有錯過殺棋」與「有沒有走進被殺」。

### 8.4 為什麼

每一個疑問手以上的標記，要附一句原因。原因由規則判斷，依序檢查，用第一個成立的：

1. **走進被殺**：這一步之後對方有 n 步殺。
2. **錯過殺棋**：當時有 n 步殺而沒有走。
3. **丟子**：照最佳應對，幾步之內會白白少掉某個棋子（比較實際走法與最佳走法在主要變化結束時的子力差）。
4. **錯過得子**：當時有辦法淨賺某個棋子。
5. **送吃**：把棋子走到會被吃、又沒有保護或保護不夠的地方。
6. **放掉保護**：這一步離開之後，原本被它保護的棋子會被吃。
7. **被抽將**：這一步讓對方可以將軍同時吃另一個子。
8. **局面型**：以上都不是。這時用評估明細，講變化最大的那一項，例如「這步之後你的車被堵住，活動的格子從 11 格變成 4 格」。

每一種原因是一組句型模板，填入棋子、位置、步數。模板放在語系檔。

### 8.5 配合程度

程式維護一個「使用者的程度」，分五級（入門、初學、中等、熟練、高手）。

估計方式：每覆盤完一盤使用者自己下的棋，算這盤的平均損失勝率與大漏著的頻率，換成一個分數，跟之前的分數做加權平均（新的佔三成）。至少三盤之後才顯示程度；之前當作「初學」。使用者可以在設定裡手動指定，手動指定之後不再自動更新，直到他按「重新估計」。

程度影響三件事：

| | 入門、初學 | 中等 | 熟練、高手 |
|---|---|---|---|
| 標記哪些步 | 只標失誤與大漏著 | 加上疑問手 | 全部，包含緩著 |
| 講解的寫法 | 完整的句子，講出具體的後果，不用術語；每個標記只講最重要的一個原因 | 用一般的象棋用語 | 精簡，直接給變化 |
| 建議的對手難度 | 比估計的程度低一級起 | 同級 | 同級或高一級 |

匯入別人的棋譜時，不更新程度；講解的深度照使用者目前的程度。

### 8.6 即時勝率

對弈中可以打開「即時勝率」：畫面邊上一條勝率條，每走一步更新。預設關閉，因為它等於在下棋時偷看答案。打開時這一盤標記為「有輔助」，不計入程度估計。

### 8.7 推演

覆盤時，使用者可以在任何一步拖動棋子走別的走法：

- 走了之後，引擎回應對方的最佳應對，並顯示這條線的勝率。
- 使用者可以繼續走、可以讓引擎替雙方各走幾步、可以退回任何一個節點。
- 所有走過的分支形成一棵樹，顯示在棋譜旁邊，可以點選跳轉。
- 分支可以加一句自己的註解。
- 這棵樹會存進這盤棋的紀錄，也會進筆記。

## 9. 筆記

使用者說筆記「還沒有想好要怎麼做」。這一節是第一版的提案，做出來給他看，之後照他的意見改。

覆盤結束按「產生筆記」，輸出一份 Markdown 檔（他平常用 Markdown 的筆記庫），內容：

1. 標頭：日期、雙方、結果、開局名稱（認得出來的話）、分析用的引擎。
2. 勝率曲線圖（內嵌的 SVG）。
3. 一段摘要：這盤棋大致怎麼發展、勝負的轉折在第幾步。由模板產生。
4. 關鍵時刻：損失最大的三到五步。每一個有：局面圖（SVG）、實際走法、更好的走法與變化、原因。
5. 使用者在推演時走過、而且加了註解的分支。
6. 這盤棋的毛病分類統計：丟子幾次、漏殺幾次、送吃幾次。
7. 一行「下次注意」：出現最多次的那一類毛病。
8. 完整棋譜（中文記譜）與起始 FEN，方便貼到別的地方。

另外提供「複製成純文字」與「下載 SVG 圖」。

所有的棋局、分析結果、筆記存在瀏覽器的本機儲存空間（IndexedDB），可以整包匯出成一個檔案、再匯入。

## 10. 畫面

繁體中文。四個主要畫面：

- **對弈**：棋盤（紅方在下，可以翻轉）、雙方的吃子、棋譜、悔棋、認輸、提和、難度選擇、即時勝率開關。
- **覆盤**：棋盤、勝率曲線（可以點）、棋譜與分支樹、目前這一步的分類與原因、候選走法清單、「想更久」。
- **匯入**：一個貼上文字的框、格式判斷的結果、錯誤訊息。
- **棋局庫**：下過與匯入過的棋，可以搜尋、刪除、匯出。

其他：棋子用圓形加文字畫，紅黑兩色；觸控可以用（點起點再點終點，也可以拖）；最後一步有標示；被將軍時有提示；可以選的落點有提示（可以在設定關掉）；畫面寬度小於 640 像素時棋盤在上、其餘在下。

引擎在 Web Worker 裡跑，搜尋中畫面不能卡住，而且隨時可以取消。

## 11. 之後包成 App

這一版只要求：網頁可以離線使用，並且可以「安裝到主畫面」（PWA）。

之後的方向（這一版不做，但現在的設計不能擋住它）：用 Tauri 把同一份網頁包成桌面與手機 App；App 版的引擎可以用原生的 Rust 直接跑，不經過 WebAssembly，並且可以啟動本機的 Pikafish。所以畫面跟引擎之間只能透過一層訊息介面溝通，不能直接呼叫 WebAssembly 的函式。

## 12. 還沒決定、需要使用者看過再定的

- 勝率分類的門檻（第 8.3 節的數字是起點）。
- 程度的五個等級怎麼對應到一般人理解的棋力。
- 手機 App 棋局的支援範圍（要等你查完）。
